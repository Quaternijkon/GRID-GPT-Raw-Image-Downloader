# Architecture

GRID Media Exporter is a client-only Chrome Manifest V3 extension. `manifest.json` loads dependency-free content scripts on the corresponding ChatGPT, Grok or Gemini pages; `background.js` receives validated download requests and calls `chrome.downloads` so files can be placed in subfolders.

## Gemini Library

`gemini-media.js` is loaded on `gemini.google.com`, and `gemini-content.js` displays its export button only on `/library`. The `/images` route is Gemini's creation screen, not its historical gallery. The Library media list uses the site's `jGArJ` batched RPC with a 30-item cursor and a ten-field media filter. The collector reads every page and rejects repeated cursors or malformed image records. Gemini can refresh a signed `/gg/` address for the same image and can reuse one `rc_` resource ID for distinct image versions in the same answer. The collector therefore deduplicates by resource, conversation, response and the page's stable variant marker. It keeps the most recently supplied permitted URL for repeated sightings and assigns deterministic hashed suffixes when multiple variants share one resource ID. Single-variant IDs remain unchanged for resume compatibility. Global image numbers are oldest-first by creation time and final stable identity. The request validation token comes from the current page's bootstrap script, remains in memory and is never written to a report.

Optional prompt export reads distinct `c_` conversations with the `hNvQHb` RPC. Each image's `r_` response ID must exactly match a returned turn before that turn's user text becomes its prompt. Missing or unavailable matches remain unresolved and their images are placed in `<folder>/未解析`. Resolved prompts use the same content-addressed group names as ChatGPT and Grok. The prompt stage does not infer text from titles or neighboring images.

The Library list supplies a Googleusercontent `/gg/` media key. `background.js` resolves the full-size `=d-I?alr=yes` chain only across `lh3.googleusercontent.com` and `lh3.google.com`, checks the final byte signature, hashes the exact bytes and submits a data URL to Chrome. It never substitutes a 320-pixel thumbnail or re-encodes the image. The worker owns all `chrome.downloads` calls. Its local progress records are keyed by folder and prompt mode, then rechecked against Chrome completion, existence and path before automatic resume. Retry overwrites the deterministic filename; a newly resolved prompt removes an older `未解析` image only after the grouped replacement has completed. Result JSON distinguishes accepted, completed, pending and failed downloads. `media-export-ui.js` provides the shared Grok/Gemini settings and progress panels, including report-based failed-item recovery and the common adaptive/manual concurrency controls.

## Grok Imagine

`manifest.json` loads a separate `grok-media.js` and `grok-content.js` flow on `grok.com`. The current `/imagine` route selects owned media; `/imagine/saved` and `/imagine/favorites` select saved media. ChatGPT scripts are never injected on Grok, and Grok scripts are never injected on ChatGPT.

`grok-media.js` reads every cursor page from the current `GET /rest/assets` Imagine workspace API, filtering generated assets. These assets often omit `mediaGenInput` and every prompt field even in `GET /rest/assets/{assetId}`. Optional prompt export groups them by `sourceConversationId`, reads `GET /rest/app-chat/conversations/{id}/responses?conversationKind=CONVERSATION_KIND_IMAGINE`, matches the exact asset ID in an assistant response's attachment fields, and follows its parent response chain to the linked human message. Owned pages prefer the assets API and can fall back to `POST /rest/media/post/list`; saved pages prefer the explicit liked-post filter and can fall back to the assets API used by Grok's newer saved view. A later-page error, repeated cursor, changed response shape, invalid creation time or conflicting media identity blocks a misleading complete export. Stable numbers come from creation time and media ID. Nested post images and videos are deduplicated by ID. Prompt groups use the existing content-addressed identity; media with unresolved prompts goes to `<folder>/未解析`.

Grok media URLs are limited to HTTPS on `grok.com`, `assets.grok.com` and `imagine-public.x.ai`. V2 `key`, `hdKey` and `hd1080Key` values can be relative paths such as `users/...`; these resolve against `https://assets.grok.com/`, as the Grok page's `ASSET_SERVER_URL` does. The content script fetches them with the current page's session only where needed, checks response bytes for a supported image or video signature, then hands a temporary blob URL to `background.js` for a validated Chrome download. The blob URL remains live until Chrome reports completion or interruption. No canvas conversion or video transcoding occurs. Video hashes over 64 MiB are omitted and called out in the report to avoid a large duplicate memory allocation. Media and prompt progress records contain only stable IDs, media sequence, paths and Chrome download IDs, keyed independently from ChatGPT by Grok scope, output folder and prompt mode. The next run verifies completion, file existence and path before skipping any ID. A retry overwrites its stable filename. If a previously unresolved prompt becomes available, the grouped file must finish writing before the worker removes the old file from `<folder>/未解析`; legacy sibling recovery files are accepted and moved into the chosen folder on retry. A cleanup failure leaves an explicit partial-layout error. Unresolved prompts also make the report's overall status partial even when every original media file completed. The settings dialog shows the locally completed contiguous sequence, and the JSON report records the verified sequence at start and finish, alongside separate queued, completed and failed counts.

The Grok image and video stage uses `download-queue.js` with the same Auto congestion controller as ChatGPT. API metadata `sizeBytes` and dimensions provide a planned per-task memory cost; the queue admits tasks in stable order only while the sum of active costs stays within a device-aware budget. One oversized video may run alone. The controller starts with up to eight tasks, probes higher throughput, backs off on slow or transient responses, and honors a manual limit of 1–12. A route change stops new admissions while in-flight tasks drain. Prompt reads and TXT writes remain a separate paced stage. The Grok result report records requested mode, final target, peak active tasks, peak planned bytes, elapsed time and adjustment history.

The export flow in `content.js` collects API image pages, validates the complete set, assigns stable oldest-first global numbers, optionally reconstructs prompt groups, and then submits original image bytes to Chrome. It writes metadata and a result report with explicit partial failures. A queued download means Chrome accepted the request; it does not prove the file finished writing to disk.

| Module | Responsibility |
| --- | --- |
| `image-lists.js` | Paginated gallery and Library collection with partial-result diagnostics. |
| `image-numbering.js` | Full-set file-ID deduplication, creation-time ordering, and contiguous completed-prefix selection. |
| `original-images.js` | Same-origin authentication, original-resource resolution, byte validation and quality measurements. |
| `prompt-conversations.js` | Bounded conversation reads, fixed ten-second serial pacing and an additional ten-second shared wait after HTTP 429. |
| `prompt-resolver.js` | Structural prompt recovery from real output ancestry, including reference-image and text-only requests. |
| `prompt-groups.js` | Exact cumulative-text grouping and the fixed `未解析/` fallback. |
| `download-queue.js` | Image-stage Auto/manual admission; independent from prompt-reading concurrency. |
| `download-progress.js` | Progress dashboard and transfer-rate estimates. |
| `background.js` | Validated local download paths, prompt TXT overwrite policy, Chrome download acknowledgements, and local progress records. |

Automatic resume stores one small extension-local record per accepted image download, keyed by normalized page route, output folder, prompt mode and global sequence. Each record holds the stable file ID, Chrome download ID and requested relative path. The settings dialog and each new run query Chrome's download history: only a completed, still-existing file at the expected path (including Chrome's ` (N)` uniquify suffix) counts as finished. The full authoritative list is always read and numbered first; the resume boundary is the longest contiguous prefix whose stored file identities match that list. A queued, interrupted, deleted or moved download stops the prefix; a still active transfer blocks a new automatic run until it finishes. Prompt and image modes have independent state because their output layouts differ. A manually chosen boundary is stored with its boundary file ID as an asserted starting point, and is rechecked against the authoritative list on later runs. For pre-upgrade exports, the worker uses its stored canonical index to match stable identities and paths against completed Chrome download history, then persists matching download IDs. If both the progress records and a verifiable canonical index are absent, automatic mode starts at zero unless the user supplies a manual boundary.

Prompt TXT records use the content-addressed group name and Chrome download ID. In automatic prompt mode, prompt collection still reads the full numbered history, then saves selected groups plus any group without a completed TXT. Image-only retry and prompt relocation replace the tracked image ID only after their replacement download completes. Progress records contain no image bytes, prompt text or authentication data. Result reports distinguish the observed completed prefix from images merely queued by Chrome.

The extension sends no data to an unrelated service. It uses each site's authenticated session only for that site's APIs and media hosts. Session tokens stay in memory and are not written to reports. Raw ChatGPT conversation bodies are not exported; prompt text and limited provenance are included only when prompt export is selected.

Image-list identity and an original download URL do not prove that the corresponding output message still exists in the conversation mapping. Missing output identity, unsupported structure and unavailable originals remain explicit failures rather than inferred prompts or thumbnail substitutions. HTTP 429 pauses prompt reads and retries the same conversation; other bounded network errors and structural errors are reported separately. In-memory prompt progress is lost when the page closes or reloads.

Original-image resolution first cycles through fresh descriptor endpoints and explicit original candidates for up to three rounds. If those rounds end only because of transient network, timeout, HTTP 408/429 or 5xx failures, `content.js` keeps the task nonterminal and places it into a serialized recovery lane for up to twelve additional rounds. The recovery lane applies shared congestion backoff and prevents multiple already-admitted tasks from retrying simultaneously. Permanent missing/invalid originals still fail promptly; successful images are never downloaded again.

Regression definitions are in `tests/` and use Node's built-in test runner. A live authenticated end-to-end run depends on the current ChatGPT account and browser state.

The prompt collector uses one full-conversation request at a time. It waits ten seconds after each completed request and another ten seconds after HTTP 429; a longer service Retry-After wins. It keeps the same conversation pending through 429 rather than marking later conversations failed. The image gallery list and sampled original PNG metadata do not carry the exact cumulative user prompt, and opening the native media viewer produced no alternate prompt-detail request in the observed account.

## Prompt-only retry

`prompt-retry.js` accepts a prior schema-4 result exported with prompts enabled or a prior prompt-retry result. It checks the current ChatGPT route, output folder, image sequence, file/conversation identity, previous recovery path and Chrome download ID before any authenticated read. Prompt groups use a content-addressed identity derived from exact normalized text, so a recovered prompt has the same destination as an initial success. New unresolved originals live in `<folder>/未解析`; legacy sibling paths remain valid retry inputs. Recovery writes the shared `prompt.txt`, retrieves the original again, waits for the final grouped download to complete and asks `background.js` to remove the old unresolved file. A failed placement or cleanup leaves the prior image and checkpoint in place. If original bytes were never retrieved, no image file can be placed in `未解析`; that failure remains explicit in the report and original-only retry checkpoint.

After a prompt-enabled run, `content.js` reduces unresolved records to a route-scoped checkpoint containing only image/conversation identities, numbering, the expected `未解析/` path and safe error diagnostics. `background.js` validates and stores at most ten checkpoints in extension-local storage. The settings dialog offers the matching page's checkpoint as a one-click retry; users may still import an exported result if local extension state was cleared. Errors consistent with temporarily incomplete conversation data receive one automatic paced reread in the same run before they enter the checkpoint.

Terminal original failures use a separate route-and-folder checkpoint containing the exact sequence, file identity, original name and final group destination. Retrying this checkpoint bypasses image discovery and conversation reads. Successful retries overwrite the exact intended path; unresolved successes also update the prompt checkpoint with their new download ID. Legacy schema-4 result imports retain numeric group destinations, while new exports use content-addressed groups.

Every completed layout also has a canonical `grid-index.json` with `layoutVersion: 2`. The extension stores a minimal copy in local extension storage and overwrites the on-disk index after normal export, prompt relocation or original-only retry. Entries exclude volatile process fields and describe only stable identity and final state. Incremental exports merge into an existing canonical index; if the base index is missing, they do not invent a complete index from a partial range.

After a prompt-placement failure, canonical state retains the image's actual `未解析/` path and unresolved status. A later successful retry updates the same identity to the exact group, filename and prompt state produced by first-run success. An empty `未解析` directory may remain after its last file is removed because Chrome's downloads API does not remove directories.

`scripts/reconcile-legacy-export.js` reconstructs legacy first-occurrence numeric grouping from existing group `prompt.txt` files and recovered numbered sidecars. It creates a separate sibling export with hard-linked or cloned original bytes, canonical group prompts, an updated reconciliation report and `grid-index.json`; it never mutates the source export.
